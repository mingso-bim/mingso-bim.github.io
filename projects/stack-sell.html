01 · MOBILE INPUT

Floating Joystick

화면을 터치한 위치에 조이스틱이 생성되고, 드래그 방향을 이용해 캐릭터를 이동하도록 구현했습니다.

IMPLEMENTATION

모바일 터치 입력과 CharacterController 이동 연결

IPointerDownHandler, IDragHandler, IPointerUpHandler를 이용해 Floating Joystick을 직접 구현했습니다.

조이스틱 입력은 CharacterController 기반 캐릭터 이동에 전달하며, 개발 중 Editor 테스트를 위해 WASD 입력도 함께 사용할 수 있도록 구성했습니다.

02 · GAMEPLAY

Collect · Stack · Sell

생성 존에서 아이템을 수집해 적재량 한도까지 쌓고, 판매 존으로 운반하면 Stack의 아이템이 하나씩 판매되도록 구현했습니다.

STACK

적재량에 따라 아이템 순차 배치

수집한 과일을 Stack Root 아래에서 관리하고, 일정 간격으로 배치해 캐릭터 뒤에 쌓이도록 구현했습니다. Capacity에 따라 최대 수집 개수를 제한합니다.

SELL

Stack 상단부터 순차적으로 판매

판매 존에 머무르면 Stack 상단의 아이템부터 하나씩 판매대로 이동하고, 판매 애니메이션이 끝나면 원래 풀로 반환됩니다. 판매된 수량만큼 Gold가 증가합니다.

OPTIMIZATION · OBJECT POOLING

Object Pooling Optimization

수집·판매 루프에서 반복되던 아이템 생성·파괴를 재사용 구조로 변경하고, 실제 게임 로직을 그대로 사용하는 자동화 벤치마크와 Android 실기기 측정으로 개선 효과를 검증했습니다.

  • Galaxy S25+ 반복 구간
  • GC Alloc −16.2%
  • 할당 이벤트 −21.1%
  • Frame Time 변화 없음

STRUCTURE

Instantiate / Destroy → Pool.Get / Pool.Release

BEFORE
  1. SSItemZone
  2. Instantiate
  3. Collect
  4. Sell
  5. Destroy

아이템 1개를 수집·판매할 때마다 GameObject가 1개 생성되고 1개 파괴됩니다.

AFTER
  1. SSItemZone
  2. Pool.Get
  3. Collect
  4. Sell
  5. Pool.Release

판매 애니메이션이 끝난 아이템은 비활성화되어 원래 생산 존의 풀로 반환되고, ↺ 다음 수집에서 재사용됩니다.

DESIGN DECISIONS

기존 구조를 활용하고, 재사용이 만드는 문제를 먼저 검토

01 · POOL OWNERSHIP

생산 존별 독립 풀

SSItemZone이 이미 아이템 프리팹을 관리하고 있어, 존마다 ObjectPool<SSItem>을 소유하도록 설계했습니다. 전역 PoolManager나 프리팹 조회용 딕셔너리 없이 기존 구조를 그대로 활용합니다.

SSItem이 자신을 만든 풀을 기억하므로, 판매 존은 아이템 종류를 판단하지 않고 ReturnToPool()만 호출합니다.

전역 매니저 · MonoBehaviour 풀 · 데이터 기반 조회 방식과 비교 후 선택

02 · COROUTINE LIFECYCLE

재사용 객체의 이동 코루틴 정리

기존에는 아이템이 파괴되면 null 검사로 스택 이동 코루틴이 스스로 종료됐지만, 풀링 후에는 객체가 파괴되지 않아 이전 코루틴이 남을 수 있습니다.

부모 Transform 검사는 재사용된 아이템이 같은 stackRoot에 다시 붙으면 통과해 버리므로, 아이템별 코루틴 핸들을 보관하고 RemoveOneItem 시점에 StopCoroutine으로 중지하도록 설계했습니다.

실제 발생한 버그가 아니라, 설계 단계에서 검토해 예방한 잠재적 문제입니다.

03 · PREWARM 0

최초 생성과 재사용 비용 분리

프리웜을 하면 최초 생성 비용이 측정 전 초기화 단계로 옮겨질 수 있습니다.

첫 사이클은 신규 생성(생성 5회), 이후 사이클은 반환된 객체 재사용(생성 0회)이 되도록 프리웜을 0으로 두었습니다.

이번 실험의 비교 가능성을 위한 결정이며, 실제 서비스에서 프리웜이 불필요하다는 의미는 아닙니다.

INTERPRETATION

확인한 것과 확인하지 못한 것

Unity Editor 전체 측정에서는 사이클당 약 16MB가 기록되어, Editor 자체 할당과 풀링 효과를 구분할 수 없었습니다. 이를 보완하기 위해 같은 러너로 Galaxy S25+에서 동일 조건으로 재측정했습니다.

확인

객체 재사용

Editor Profile Analyzer 재사용 구간에서 PoolCreateItem 호출 0회, PoolGetItem / PoolReleaseItem GC Alloc 0B를 확인했습니다.

확인

관리 힙 할당 감소

실기기 반복 구간에서 사이클당 440B, 할당 이벤트 15회가 감소했습니다 (아이템당 평균 88B / 3회). 같은 변경에 코루틴 관리 코드도 포함되어 있어, 전부 Instantiate 제거의 효과라고 단정하지 않습니다.

확인되지 않음

프레임 시간 개선

아이템 처리 비용이 16.67ms 예산에 비해 작아 시간 지표에 드러나지 않았습니다. GC 실행 횟수는 수집하지 않아 GC 스파이크 감소도 주장하지 않습니다.

측정 한계: Development Build · 기기 1대 · 아이템 1종 · 적재량 5 고정 시나리오 · 첫 사이클의 생성 비용과 스파이크는 풀링 후에도 유지
